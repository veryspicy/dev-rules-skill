# 通用软件开发规则手册

> 适用于 AI 助手在任意项目中的所有开发协助行为。
> 使用本 Skill 时，凡出现 `<项目根目录>`、`<容器名>`、`<compose 文件>` 等占位符，一律替换为当前项目的实际值（路径、容器名、命令格式以项目实际状态为准，禁止凭记忆假设）。

---

## 1. 版本管理（Git Flow）

遵守 Git Flow 工作流：

- **feature/** 分支：新功能
- **fix/** 分支：Bug 修复
- **hotfix/** 分支：紧急修复
- 合并路径：feature/fix → dev → main
- 提交信息遵循 Conventional Commits 规范
- 禁止创建备份文件（如 `*_backup.py`、`*_old.py`、`*_20260629.py` 等带时间戳后缀的文件）

### 1.1 前置约束：分支必须归集到 dev

**铁律**：每次开始新的 fix 或 feature 开发前，必须先将所有本地分支合并归集到 dev，再从 dev 创建新分支。

**执行步骤**：

1. **检查遗留分支**：`git branch --no-merged dev`
2. **逐一合并或删除**：
   - 有独有提交的分支 → `git merge <branch>` 合入 dev
   - 提交已是 dev 某 commit 的 cherry-pick 等价版 → `git branch -D <branch>` 直接删除
3. **确认归零**：`git branch --no-merged dev` 必须无输出
4. **从 dev 创建新分支**：`git checkout -b fix/<xxx>` 或 `git checkout -b feature/<xxx>`

**cherry-pick 等价判定**：用 `git log --grep="<关键词>" dev` 在 dev 历史中搜索相同功能的 commit，若 commit message 和改动内容一致（仅 SHA 不同），则该分支可安全删除。

**挂起分支例外**：若存在已开发完成但**用户尚未验证通过**的分支，允许不合并它直接从 dev 另开新分支继续开发；新分支改动与挂起分支无交集时不受影响。挂起分支必须在会话中持续追踪，验证通过后按 1.3 合并，禁止遗忘。

### 1.2 合并 dev 验证门禁（强制）

**铁律**：用户明确验证通过之前，禁止将 fix/feature 分支合并到 dev，更禁止 push origin dev。用户说"部署 dev / 部署到 dev / 我要验证"等指令时，语义是**先部署最新代码供用户验证**，不是授权合并提交。

**执行步骤**：

1. 功能分支开发完成后，先本地部署（重建镜像 + 重建容器）供用户验证
2. 用户明确回复"验证通过 / 可以合并 / 提交 dev"等确认语后，才允许 `git merge <branch>` 到 dev 并 push origin dev
3. 用户未验证或验证未通过 → 分支保持本地（可 push 远程功能分支，但**不得**合入 dev），继续修复直至用户确认
4. 部署验证与合并提交是两件事，禁止混为一谈：先部署 → 用户验证 → 再合并

## 2. 缓存清理与重启

**触发条件**：修改以下类型文件后，由 Agent 判断是否需要清除缓存并重启：

| 文件类型 | 是否需要清缓存 |
|---|---|
| `server/` 目录下的 `.ts` 文件（Nitro 路由/中间件） | **是** |
| `nuxt.config.ts`、`package.json` | **是**（且需重建镜像） |
| `pages/`、`components/`、`composables/` 下的 `.vue` / `.ts` | 否（HMR 自动生效） |
| `stores/` 下的 `.ts` 文件 | 否（HMR 自动生效） |
| `locales/` 下的 `.json` 翻译文件 | 否（HMR 自动生效） |
| Dockerfile、`docker-compose.yml` | 参考第 3 节 |

**通用原则**：
- 框架内部生成物（如 `.nuxt`、`node_modules/.cache`）在重启前需清理，避免旧产物干扰
- 后端源码若为 bind mount 挂载，直接重启容器即可生效
- 容器生命周期操作统一使用项目约定的 compose 命令，禁止散用底层命令

## 3. 部署策略

### 3.1 通用判断矩阵

| 变更内容 | 操作 |
|---|---|
| 前端源码（`.vue` / `.ts` 等）、翻译文件 | HMR / 重启容器即可，**无需重建镜像** |
| `Dockerfile`、`package.json`、构建配置、依赖锁文件 | 必须重建镜像，且只重建受影响的服务 |

### 3.2 无 HMR 的静态构建端（重要）

若项目存在无热更新的静态构建端（如 Vite 构建产物由 nginx 直接服务）：

| 变更内容 | 操作 |
|---|---|
| **任何源码** | 必须 `build --no-cache` 重建镜像 + `up -d --force-recreate` 重建容器 |

> **为什么需要 `--no-cache`**：Docker 层缓存可能命中旧的 `COPY . .` 层，导致源码改动未打入镜像。容器重建后用户还需硬刷新浏览器绕过 CDN 缓存。

### 3.3 通用命令约束

- 容器生命周期管理（up/down/start/stop/restart/logs 等）统一用 compose 命令
- **容器内执行命令**（如迁移、调试、进入 shell）使用 `podman exec <容器名> <命令>`，两者职责不同，不构成矛盾
- 容器名以 compose ps 实际输出为准，禁止凭记忆假设

## 4. 知识检索优先级

遇到不确定的事项，按以下顺序查找：

1. **查阅项目 `docs/` 目录下的文档**（架构、环境、容器、端口、SOP）
2. 文档未覆盖 → **询问用户**

禁止在无依据的情况下自行决策架构、配置或业务逻辑层面的问题。

---

## 5. 执行前计划

每次执行任务前，Agent 必须：

- **先向用户说明执行计划**（改哪些文件、做什么操作、预期结果）
- 用户知情后即可开始执行，无需逐一等待审批

**文件修改约束**：

- 修改文件本身无需用户审批
- 必须确保修改不引入新 Bug
- 修改完成后必须进行**回归测试**验证

---

## 6. 新增文件与变更记录

- 新增文件、引入新内容无需用户审批
- 每次完成任务后，必须在回复中声明产出物（使用 `yyb-product` 卡片）
- 所有文档（`.md`）必须放在 `docs/` 目录下，根目录仅允许 `README.md` 一个 Markdown 文档

## 7. 规则自增长机制

> **核心理念**：将每次踩坑经验沉淀为可复用的规则，让规则文档持续进化为项目开发专家手册。

### 7.1 触发条件

当出现以下任一情况时，Agent 必须主动评估是否需要写入新规则：

- 遇到问题经排查后成功解决，且排查过程涉及非显而易见的项目特定知识
- 用户明确指出"把这个记下来"、"下次别犯这个错"、"加一条规则"
- 重复犯过同类错误，说明旧规则未覆盖
- 发现现有规则存在错误或过时，需修正

### 7.2 写入标准

新增规则必须满足：

1. **可复用**：该经验在未来类似场景中有参考价值
2. **可执行**：规则描述具体、有明确的判断条件和操作步骤，而非模糊建议
3. **不冗余**：与已有规则不重复；若已有规则覆盖不全则更新已有规则而非新增

### 7.3 执行流程

1. **问题解决后**：先总结根因和解决方案
2. **评估可规则化**：对照 7.2 写入标准判断是否应写入
3. **定位归属章节**：找到最相关的现有章节，或在末尾新增章节
4. **写入并声明**：写入完成后在回复中用 `yyb-product` 声明更新
5. **格式要求**：每条规则包含触发条件（何时适用）、执行步骤（怎么做）、反例（常见的错误做法）

## 8. 变更行为准则

> **核心原则**：工作区是神圣的。任何一次修改都必须知道它从哪里来、要到哪里去、失败后能否回得去。

### 8.1 禁止残留：失败的尝试必须立即清除

**铁律**：修改了某个文件试图解决问题，但验证后发现无效 → **立刻还原该文件**，一秒都不能留。

理由：残留的半成品代码会在后续排查中伪装成"正常代码"，让你误以为它是原始设计的一部分。从此你排查的不是原始问题，而是你自己制造的第二个问题。

### 8.2 禁止污染：任何时候都要知道工作区里多了什么

**铁律**：在开始排查任何异常之前，**先执行 `git diff` 和 `git status`**。确认当前工作区里有哪些未提交的变更。

理由：如果工作区不干净，你无法判断异常是原始代码的问题还是未提交变更的问题。带着脏工作区排查问题是浪费时间。

### 8.3 禁止盲动：先证明问题存在，再试图修复

**铁律**：在动手改代码之前，必须先用可重复的验证手段（脚本、API 调用、自动化测试）**精确复现并定位问题**。修改只能在定位完成之后进行。

理由：没有精确复现就动手，你改的是空气。改完无法判断是"修好了"还是"恰好没触发"。

### 8.4 禁止跳跃：一次只动一个变量

**铁律**：每次只修改一个文件中的一处逻辑，修改后立即验证。验证通过才能进行下一处修改。绝不允许"先改 A，再改 B，最后一起测"。

理由：同时改多处后测试通过，你无法区分是哪一处修改起了作用；测试失败，你无法区分是哪一处修改导致了失败。无论结果如何，信息量为零。

### 8.5 禁止并行编辑同一文件

**铁律**：同一文件的多个位置修改必须**串行**执行（一次编辑完成并确认后再做下一次），禁止在同一轮并行发起多个编辑指向同一文件。

理由：并行编辑同一文件时各编辑基于同一旧快照读写，后写覆盖先写，先前的修改会静默丢失且工具仍报告"替换成功"。

## 9. 会话启动上下文恢复（强制）

**触发时机**：每次 Agent 开始处理项目任务前（新会话或用户重新提到项目），必须先执行本节校验，严禁依赖对话历史摘要代替实际 git 状态检查。

**校验清单（必须逐条执行，不可跳过）**：

1. **检查当前 Git 状态**：
   ```bash
   git status --short    # 工作区是否有未提交改动
   git stash list        # stash 栈是否非空
   git branch -v         # 所有本地分支及最新 commit
   git log --oneline -5  # 当前分支最近提交
   ```

2. **工作区不得有遗留改动**：
   - 若 `git status --short` 非空 → 必须先向用户报告有哪些未提交文件，由用户决定 commit / stash / 丢弃
   - 若 `git stash list` 非空 → 必须展示 stash 列表，询问用户是否恢复

3. **确认功能代码所在分支**：
   - 对比各分支 `git log --oneline <branch>` 和 `git diff <branch> --stat`，找出包含最新功能代码的分支
   - 禁止假设 `dev` 包含所有已实现功能；必须以实际 git 历史为准

4. **关键分支必须推送**：
   - 任何承载已验证功能的本地分支，会话结束前必须 `git push origin <branch>`
   - 若推送失败（无权限等），必须明确告知用户分支名和 commit hash

## 10. 重建后端到端验证（强制）

**触发时机**：完成容器重建/重启后，必须在用户查看结果前完成端到端验证。禁止仅凭"源码存在"或"静态资源在容器中"就宣布修复成功。

### 10.1 API 路径一致性检查

对比前端 API 调用路径与后端实际注册路由，确保二者一一对应：

| 检查项 | 方法 |
|--------|------|
| 前端 API 调用路径 | 读前端 service/api 文件 |
| 后端实际路由注册 | 读后端路由注册文件 |
| 路径是否匹配 | 逐条对比，任一不匹配即为阻断 |

### 10.2 数据链路完整性检查

| 检查项 | 方法 |
|--------|------|
| 关键表是否有数据 | 容器内查询数据库对应表 |
| API 是否可达 | 容器内 curl 健康检查（需带 auth header） |
| 列表数据是否返回 | 验证返回 JSON 中关键数组不为空 |

### 10.3 需求匹配度检查

在宣称"功能正常"之前，必须回顾用户原始需求描述，逐条核对：

| 需求点 | 当前实现 | 是否满足 |
|--------|----------|----------|
| 逐条列出用户需求 | 逐条列出实际实现 | 标注满足/部分/未满足 |

**任一需求点未满足 → 必须如实报告缺口，禁止宣布"正常"。**

## 11. 开发验证流程（强制）

> **核心原则**：快速迭代优先。能用非浏览器手段自查的绝不派浏览器；必须真实浏览器确认的才派 browser-agent；能由用户实测的优先交给用户。

### 11.1 浏览器验证按必要性判断，不默认派发

1. **先用非浏览器手段自查**：容器内产物 hash/时间戳核对、关键逻辑 grep、接口级 curl 验证、源码静态检查
2. **必须派发 browser-agent 的情形**：只有依赖真实浏览器才能确认的行为——上传交互链路、登录态、多步表单、视觉布局、缓存后表现等
3. **派发时强制要求**：明确要求 browser-agent 核对加载的 JS hash 与预期构建一致，从源头排除浏览器缓存干扰
4. **能交给用户验证的交给用户**：完成代码修改与容器部署后，优先向用户说明验证点（访问地址、操作步骤、预期结果），由用户实测并反馈截图或报错文本

### 11.2 构建产物强制核对

**触发条件**：每次执行无 HMR 端的镜像构建之后。

1. **禁止以 "Build successful" 作为完成依据**——构建可能缓存命中 builder 阶段，实际构建并未真正执行
2. **核对容器内产物**：检查产物文件时间戳/hash 晚于源码修改时刻
3. **grep 关键逻辑**：容器内检查产物文件包含修复特征字符串，确认修复已进入产物
4. 核对通过后才进入验证环节

### 11.3 browser-agent 结论需复核

**触发条件**：browser-agent 返回任何"源码级"静态结论（组件存在性、代码逻辑、缺失判断等）。

1. browser-agent 的 DOM/网络证据可信，但推导出的根因结论必须经复核后才采信
2. 压缩混淆后的 JS 不保留组件名，**字符串搜索组件名不可作为存在性判据**；以编译产物中实际渲染逻辑为准
3. 涉及组件存在性等静态判断，以直接核查源码 + 编译产物为准，不盲信文本匹配结论

## 12. 临时文件与产物管理（强制）

> **核心原则**：测试产物、日志、临时文件一律放入 `temp/` 目录，禁止散落在根目录、源码目录或 docs 目录。`temp/` 已加入 .gitignore，永不提交。

1. 所有测试产物、日志、临时文件统一写入仓库根目录 `temp/` 下（`temp/` 应在 .gitignore 中忽略，不污染 git 状态）
2. 测试**源码**保留在源码 `tests/` 目录；测试**过程产生的输出**（报告、临时数据、截图、缓存）必须写入 `temp/`
3. 交付性文件（报告、文档、最终产物）不得放入 `temp/`；交付物按第 6 节在 `docs/` 或对应模块目录落地并通过 `yyb-product` 声明
4. `temp/` 下内容为一次性产物，可随时删除，不影响仓库完整性

---

## 13. 代码质量与安全检查（强制）

> **核心原则**：提交前本地快检，CI 全量兜底。每个模块提交前必须通过对应质量门槛；CI 在 dev/main 分支与 PR 上执行全量 lint / typecheck / test / audit，任一 job 失败即阻断合并。

### 13.1 各模块提交前必过命令

| 模块类型 | 提交前必过 |
|----------|-----------|
| Python 后端 | ruff check、ruff format --check、mypy（或项目约定的等价工具） |
| Node 前端 | lint、typecheck、fmt（或项目约定的等价工具） |

### 13.2 Git Hooks

- 提交信息校验由 commit-msg hook 统一兜底（conventional commits）
- 本地 hooks 执行的是提交前快检；CI 始终兜底执行同等检查，两者缺一不可
- 若项目同时存在多个 hook 框架（如 pre-commit 与 simple-git-hooks），注意它们占用同一 `.git/hooks/` 目录会互相覆盖，需明确统一由其中一个管理

### 13.3 CI 门槛

- 后端：lint + 类型检查 + 测试（含覆盖率）+ 依赖漏洞审计
- 前端：eslint + 测试 + typecheck + build + 依赖审计
- 密钥扫描：全仓密钥扫描（含历史提交）
- 镜像构建后：镜像漏洞扫描，CRITICAL/HIGH（非 un-fixed）即失败
- 所有测试 job 通过后才会进入构建与部署阶段

### 13.4 安全红线

1. 密钥、Token、密码严禁入库（密钥扫描会检查历史提交）
2. 新增依赖必须通过对应依赖审计；发现漏洞先升级修复，禁止绕过或忽略
3. 镜像存在 CRITICAL/HIGH 可修复漏洞时不得发布部署

### 13.5 提交前本地验证与集成测试契约核查（强制）

> **核心原则**：质量门槛必须在首次提交前一次性通过，禁止用"提交→被 hook 拦截→修复→再提交"的循环逼近；集成测试必须基于契约编写，禁止试错式探测。

1. **提交前用 hook 同参验证**：取暂存文件后，用与 hook 配置完全一致的参数跑 lint / format / type check，全过后再 commit
2. **commit 被 hook 拦截时**：禁止盲目重复 commit；先显式运行 hook 定位最后一个失败项，按输出修复后一次通过
3. **集成测试前置契约核查**：先查契约再写断言，禁止边跑边猜：

4. **插入测试数据时显式提供全部 NOT NULL 列**（id、时间戳、状态位等），不依赖 server_default 兜底
5. **e2e 期望值与契约一致**：403/401/307 必须按实际路由与中间件行为断言，不臆测
6. **批量替换后的残留核查**：用脚本/正则批量替换后，全局 grep 确认无残留旧符号，避免运行期 ImportError

## 14. 数据与发布安全（强制）

> **核心原则**：数据库变更与生产发布是不可逆操作的高危区，任何变更必须可回滚、可恢复、可验证。

### 14.1 数据库变更（migration）流程

**触发条件**：任何涉及数据库结构变更（建表、改列、加索引、种子数据）的改动。

1. **在容器内执行 migration，禁止本地直连数据库**：`podman exec <后端容器名> alembic upgrade head`
2. 变更前必须先备份目标库（见 14.2）
3. migration 脚本必须经 review：逐条核对列变更与业务需求的对应关系，确认无多余 DDL
4. 执行后立即验证：关键表结构、数据完整性（count 抽查）
5. 失败回滚：`alembic downgrade -1`；仍失败则从备份恢复（14.2）

### 14.2 数据备份策略

**触发条件**：任何重要数据变更前，以及每周例行全量备份。

| 数据 | 备份方式 | 频率 |

| 对象存储 | 关键目录同步至备份位置 | 每周 |

- 备份文件命名带日期，保留最近 3 份
- 每季度至少做一次恢复演练：从备份恢复到临时库并验证数据可用

### 14.3 部署回滚方案

**触发条件**：线上部署后出现阻断性故障。

1. 镜像按 commit sha 打 tag，回滚即把 deployment 的 image 指回上一个已验证 sha
2. 若故障由 db migration 引起，先按 14.1 回滚 migration（downgrade 或恢复备份）

## 15. 版本发布与提交规范（强制）

> **核心原则**：提交信息统一 Conventional Commits；发布走语义化版本（vMAJOR.MINOR.PATCH）+ 不可变镜像 tag。

### 15.1 语义化版本与镜像 tag

| 触发事件 | 镜像 tag | 说明 |
|---------|---------|------|
| 主干分支 push（日常合并） | commit sha | 不可变、可追溯，用于验证与回滚 |
| `v*` tag push（正式发布） | 语义版本号（如 v1.2.0） | 发布快照，构建后不自动部署 |

1. 版本号规则：`vMAJOR.MINOR.PATCH`
   - MAJOR：不兼容的 API 或破坏性变更
   - MINOR：向后兼容的新功能
   - PATCH：向后兼容的缺陷修复
2. 发布流程：验证通过并合并主干后，在主干上打 tag：`git tag v1.2.0 && git push origin v1.2.0`
3. CHANGELOG.md 维护在仓库根：`Unreleased` 段记录未发布变更，发布时将内容归档到对应版本号并清空

### 15.2 Commit Message 规范（Conventional Commits）

**格式**：`<type>(<scope>): <subject>`，如 `feat(portal-web): 增加订单列表筛选`

**允许 type**：feat / fix / docs / style / refactor / perf / test / build / ci / chore / revert

合并 PR 的 squash message 同样必须符合规范。
